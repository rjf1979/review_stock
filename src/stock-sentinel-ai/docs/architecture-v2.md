# 智诊盯盘架构改造方案

## 结论

现有 Node 单进程同时承担静态页面、HTTP API、证据计算和批量 AI 研判，批量任务会占用事件循环，导致页面与弹框响应变慢。改造目标是将页面 API 与研判 Worker 分进程，采用有限并发和单写入队列。

## 目标架构

```text
浏览器
  -> API/静态服务（Node，3110）
       -> 本地 SQLite 只读查询
       -> 任务控制接口
       -> SSE 批量状态推送
       -> Worker IPC/本地 HTTP
            -> 研判 Worker 进程池（默认 3 路）
                 -> 本地 K 线与证据计算
                 -> AI 请求限流、超时、重试
                 -> SQLite Writer 单写入队列
```

## 进程边界

### API 服务

- 只处理静态资源、详情查询、候选池查询和任务控制。
- 不执行批量指标、价位或 AI 调用。
- 详情读取优先使用本地 SQLite；实时源只用于显式补数。
- 页面状态通过 SSE 推送，轮询作为降级方案。

### Worker

- 启动时冻结候选池代码和证据版本。
- 先快速生成任务清单，再按并发上限执行。
- 每只股票独立超时、失败隔离、可重试。
- 在任务入口执行 60 分钟冷却和闭市锁定。
- 每只股票完成后发送 `stock.completed` 事件。

### SQLite Writer

- 所有研判、价位、批次状态写入集中到一个队列。
- 事务提交后异步刷盘，完成事件在刷盘成功后发送。
- API 服务只读打开数据库，避免和 Worker 争抢写锁。

## 状态事件契约

```json
{
  "event": "stock.completed",
  "batchId": "batch_xxx",
  "code": "301171",
  "status": "success|failed|skipped|cooldown|closed_locked",
  "persisted": true,
  "finishedAt": 1788500000000,
  "message": ""
}
```

`persisted=true` 是页面显示“已保存”的唯一依据，不能仅按内存任务计数。

## 并发策略

- AI 调用默认并发 3，设置页允许 1～5。
- 行情补数默认并发 8，但每个数据源单独限流。
- 指标/价位计算放入 Worker 的线程池；SQLite 写入不并发。
- 单票准备超时 15 秒，AI 请求超时沿用接口配置；失败只影响当前股票。
- 同一代码在同一批次禁止重复执行。

## 分阶段实施

1. **Worker 拆分**：新增独立 Worker 入口，API 服务通过本地 IPC/HTTP 启停和读取状态；保持现有业务函数与 SQLite schema 不变。
2. **写入队列**：将研判记录、价位和批次快照统一交给 Writer，逐票确认刷盘后再推送完成事件。
3. **有限并发**：Worker 引入 3 路并发、超时、重试和冷却/闭市判断；前端列表按事件即时更新。
4. **SSE 推送**：新增 `/api/ai/batch-events`，前端连接断开时回退 `/api/ai/batch-status`。
5. **Python 评估**：只有 Node Worker 稳定并完成结果一致性对比后，才迁移为 FastAPI + Python Worker；不改变前端协议和数据库契约。

## 验收标准

- 批量研判运行时，页面 API P95 响应小于 500ms。
- 每只股票完成后 2 秒内列表状态更新为已保存/失败/跳过。
- Worker 异常退出后，已刷盘结果可恢复，未完成任务可续跑。
- 同一证据不会重复调用 AI，60 分钟内不会二次研判，闭市最终记录不会重跑。
- 全量测试、数据库一致性检查和 375/768/1440px 页面检查通过。
