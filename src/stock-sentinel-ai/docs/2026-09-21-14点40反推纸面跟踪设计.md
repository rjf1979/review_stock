# 14:40 分时反推 → 次日早盘卖出：纸面跟踪通道设计

状态：设计已定稿，工具与调度脚本随之落地（2026-09-21）。
适用子项目：智诊盯盘 `src/stock-sentinel-ai/`。

## 1. 为什么是「纸面跟踪」而不是实盘下单

回测批次 `runId=11`（`runKey=reverse-20260612-20260917-stockonly-t1440`）只用
**69 个交易日**（20260612~20260917）、298,294 笔样本完成拟合，模型自带的口径红线仍然成立：

| 红线指标 | 实测值 | 含义 |
| --- | --- | --- |
| `usableForDecision` | `0` | 模型文件自报「不可作为下单依据」 |
| 样本长度 | 69 个交易日 | 不足一个完整的市场周期，月度稳健性只有 4 个月 |
| 最高十分位样本外命中率 | 预测 48.96% / 实际 42.32% | 有过拟合迹象 |
| 最高十分位样本外策略均值 | −0.253% | 扣 0.15% 单边摩擦后仍是负收益 |

所以本通道的定位是**纸面跟踪**：每个交易日生成候选、逐笔回填真实结果，用实盘样本继续
检验这套概率，等样本外表现转正且用户单独确认后，才谈得上替换 3110 的生产模型
（`decision_model.json` + `probability-engine.js`）。设计文档与界面文案都必须显式回报这条红线。

## 2. 通道命名与共存策略

`data/kline.db` 的 `bt_decision` 对 `(tradeDate, code)` 建了唯一键，两套通道写同一天会互相覆盖，
因此用 `source` 字段把通道分开，并在写入前做预检：

| 字段 | 本通道取值 | 说明 |
| --- | --- | --- |
| `source` | `reverse-1440` | 与既有 `pool`（入池固化）通道区分 |
| `runId` | `11` | 取自 `bt_run`，即 14:40 分时反推批次 |
| `runKey` | `reverse-20260612-20260917-stockonly-t1440` | 跨库追溯用 |
| `suggestedBuyTime` | `1440` | 买入锚点：T 日 14:40 一分钟收盘 |
| `suggestedSellTime` | `1030` | 卖出窗口：T+1 09:31~10:30 |

写入前先 `GET /api/decisions?tradeDate=T` 拉当日已有记录：

* 同一代码若已被 `source='pool'` 占用 → **跳过并计数**，不用本通道覆盖入池凭据；
* 同一代码若已是本通道记录 → 正常覆盖（生成阶段可安全重跑，回填结果列不受影响）；
* `saveBtDecisions()` 只更新 22 个业务列 + `createdAt`，不触碰 `actual*` / `settledAt`，
  所以重跑生成阶段不会抹掉已经回填的实盘结果。

⚠️ `storage.js` 是 sql.js 内存库 + 整文件写回。外部脚本**不得**直接写 `data/kline.db`，
一律走 3110 的 HTTP 接口（`POST /api/decisions`、`POST /api/decisions/settle`）。

## 3. 时点与调度

| 阶段 | 触发时点（Asia/Shanghai） | 动作 |
| --- | --- | --- |
| 生成 | 当日 `14:41` 之后（分钟线已含 14:40 收盘） | 打分 → `POST /api/decisions` |
| 结算 | 次日 `10:31` 之后（分钟线已含 10:30 收盘） | 计算真实结果 → `POST /api/decisions/settle` |

调度由独立 Node 进程 `scripts/paper-track.js` 承担（`npm run paper:track`），30 秒轮询、
盘中只调本地 HTTP；数据未就绪、非交易日、服务未启动时**打印原因并继续等待**，
不做破坏性兜底、不静默换端口（固定 `127.0.0.1:3110`）。

## 4. 生成口径（T 日 14:40）

与训练样本**逐字段同源**，全部复用 `tools/minute_reverse_backtest.py` 的实现，
不允许在实盘链路里另写一套特征公式：

* 股票池：`filter_stock_universe()` —— 剔 B 股 / 北交所 / 指数 / ETF、科创板、ST、银行行业、退市股；
* 分时特征 31 项：`minute_features()`，只用 ≤14:40 的 1 分钟线；14:40 已封板 → 不入选；
* 日线特征 14 项：T-1 收盘口径（涨幅/振幅/5·20·60 日收益/RSI14/ATR/5·10·20·60·120 日乖离/
  距 20 日新高/上市天数/流通市值/上市板）；
* 上下文 11 项：`bt_market_day`、`bt_sector_day` 一律取 **T-1**（当日统计量收盘后才成立）；
* 分档：用 `model.metas` 的**训练集分位边界**给新样本分档，落在训练集未出现档位 → 该特征贡献 0；
* 打分：`X = log-lift(bucket)` → `(X−mu)/sd` → `sigmoid(w·[1,Xs])`，`z` 截断 ±30；
  目标 `up1..up9`、`limitUp`；
* 规则命中：读 `model.ruleSet`（30 条：single/pair/triple 各 10 条），
  命中要求条件特征值**有限**（缺失不算命中）；
* 流动性门槛：`mAmountWan1440 ≥ 1000`（万元）后才参与 Top-K 排序，与回测模拟一致。

**数据源硬要求**：`load_minute()` 必须返回 `source == '.lc1'` 且 `origin == 'tdx-client'`。
`.01` 是分笔转档，取不到分钟内极值，一旦命中就报错退出，不用降级数据出结论。
自检：`python tools/tdx_minute.py verify --code "600519,000001" --tdx-dir D:\new_tdx`。

## 5. 结算口径（T+1 09:31~10:30）

`actual*` 六列的含义与回测的 `stratRet` 公式**完全对齐**（单位：%，已扣 0.15% 单边摩擦）：

| 列 | 公式 |
| --- | --- |
| `actualEntryPrice` | T 日 14:40 一分钟收盘价（元，不复权） |
| `actualHigh` | T+1 09:31~10:30 最高价（元，乘 `adj` 折算到 T 日口径） |
| `actualRetHigh` | `(actualHigh / actualEntryPrice − 1) × 100` |
| `actualExitPrice` | 若冲高：`max(+3%, T+1 开盘涨幅)` 对应价；否则 T+1 10:30 收盘价 |
| `actualRetExit` | 上表卖出价收益率 `− 0.15` |
| `hit3` | `actualRetHigh ≥ 3.0` → 1，否则 0 |

跨日除权用前复权因子折算（`adj = f(T)/f(T+1)`），与回测 `label_features()` 同一处理；
T→T+1 之间停牌超过 `KLINE_MAX_GAP=10` 自然日 → 该笔不结算并记警告，不猜价格。

## 6. 幂等、重试与失败处理

* 生成阶段：`(tradeDate, code)` 覆盖写，重复运行结果一致；`actual*` 列不受影响。
* 结算阶段：只接受已存在的 `(tradeDate, code)`；目标记录不存在 → 记 `skipped`，不新建空行。
* 已结算记录（`settledAt` 非空）重复结算 → 结果相同，允许重跑；数值不一致时以最后一次为准，
  但脚本会打印差异便于排查。
* HTTP 失败：指数退避重试（最多 5 次），仍失败则打印剩余未写入条数与原因后退出，
  由下一次轮询补齐（生成阶段是幂等覆盖，因此可安全重试）。
* 非交易日 / 14:40 分钟线缺失 / `.lc1` 源缺失：打印原因并跳过当日，不写半截数据。

## 7. 与回测一致性的核对方法

1. 用 `tools/minute_reverse_score.py --date T --stage generate --dry-run` 对**回测区间内**的
   某一天打分，把 58 个特征与 `samples.csv` 同日同码的行逐字段比对（容忍 1e-4 舍入）；
2. 对同一天用模型打分，与 `minute_reverse_analyze.py` 的 `loo` 预测比对，确认打分链路一致；
3. 结算阶段用 `--stage settle --date T --dry-run` 回放当日，与 `samples.csv` 的
   `hi1030Pct` / `openPct` / `c1030Pct` / `entry1440` 比对；
4. 纸面跟踪累计 ≥20 个交易日后，用 `GET /api/decisions` 的 scorecard
   （`hit3Pct`、`avgExitRet`）与回测基准 20.08% / 策略均值对照，判断是否出现口径漂移。
